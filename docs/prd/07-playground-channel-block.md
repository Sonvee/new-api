# 游乐场渠道调用限制 PRD

## 文档元信息

- 状态：已实现，待开发者手动验证
- 关联计划：[`docs/plans/07-playground-channel-block-plan.md`](../plans/07-playground-channel-block-plan.md)
- 创建日期：2026-09-19
- 目标分支：`custom`
- 最后确认范围：新增渠道级“禁止游乐场调用”配置，仅限制 `/playground` 的模型可见性和实际渠道选择

## 1. 背景与问题

当前同一用户分组下可能配置多个渠道，并且多个渠道可能同时提供同一个模型。部分渠道只适合 API 密钥、业务接口或其他调用场景，不希望被 `/playground` 游乐场使用，但现有渠道配置没有针对游乐场的独立开关。

本需求需要提供一个渠道级配置，使管理员能够在创建或编辑渠道时禁止该渠道参与游乐场调用，同时不改变其他页面和原有渠道选择行为。

## 2. 目标

1. 在“创建渠道”和“编辑渠道”弹出层的“其他设置”区域中的“渠道额外设置”下新增“禁止游乐场调用”配置项。
2. 配置默认关闭，兼容已有渠道数据。
3. 开启后，该渠道不能被 `/playground` 页面实际请求选中。
4. `/playground` 的模型选择列表只展示当前分组下至少存在一个未被禁止渠道的模型。
5. 如果某分组下所有渠道都禁止游乐场调用，该分组仍然显示，但该分组的模型列表为空，不显示模型。
6. 限制只对 `/playground` 生效，不能影响 `/keys` 配置密钥时的分组选择，也不能影响其他页面、接口或普通 API 调用。

## 3. 非目标

- 不改变渠道在 `/keys`、管理页面、普通 API、任务插件或其他业务流程中的可用性。
- 不删除或隐藏用户可用分组本身；即使分组下没有可用模型，分组仍需显示。
- 不改变渠道的状态、优先级、权重、模型配置、分组配置或既有路由策略。
- 不新增独立数据库表或外部依赖；优先复用现有渠道额外设置 JSON 和现有渠道/能力查询机制。

## 4. 用户与场景

### 4.1 角色

- 管理员或具备渠道编辑权限的用户：配置渠道是否允许游乐场调用。
- 普通用户：在 `/playground` 中选择分组和模型并发起对话。

### 4.2 主要场景

给定用户分组 `Codex旗舰`：

- 渠道 A 提供模型 1、模型 2，并开启“禁止游乐场调用”。
- 渠道 B 提供模型 1、模型 3，未开启该配置。

在游乐场选择 `Codex旗舰` 时：

- 模型 1 仍显示，但请求只能从渠道 B 的模型 1 中选择。
- 模型 2 不显示，因为该模型只有渠道 A 提供且渠道 A 被禁止。
- 模型 3 正常显示并可调用。

如果某分组的所有渠道均开启该配置：

- 分组仍显示在分组选择栏中。
- 该分组的模型选择栏为空，不显示任何模型。

## 5. 功能需求

### FR-1：渠道配置项

- 在渠道创建和编辑弹出层的“其他设置”→“渠道额外设置”中增加一个开关。
- 展示文案为：`禁止游乐场调用`。
- 默认值为关闭。
- 编辑已有渠道时，未保存该配置的历史数据按关闭处理。
- 保存时持久化到现有渠道额外设置配置中；关闭状态不得被解释为禁止。
- 该字段应遵循现有渠道表单、权限控制、表单校验和国际化约定。

### FR-2：游乐场模型列表过滤

- `/playground` 请求分组对应模型列表时，服务端只返回该分组下至少有一个“允许游乐场调用”的启用渠道所提供的模型。
- 模型以模型名称去重，保持现有模型列表的返回契约和排序习惯。
- 过滤只在游乐场专用模型列表请求路径或显式游乐场上下文中生效。
- 现有用户分组权限、分组倍率、模型可用性和其他模型过滤规则继续生效。
- `/api/user/groups` 及其他分组列表接口不因该配置过滤分组，因此无可用模型的分组仍显示。

### FR-3：游乐场实际请求选渠道

- 游乐场请求在服务端选择渠道时，必须排除已开启“禁止游乐场调用”的渠道。
- 过滤应覆盖首选渠道/亲和性选择、普通渠道选择、重试和自动分组等会实际选中渠道的路径。
- 当同一模型存在允许调用的渠道时，游乐场不得回退或重试到被禁止渠道。
- 当模型列表因并发配置变化或旧客户端仍提交了已不可用模型时，服务端仍需拒绝选择被禁止渠道，并返回现有无可用渠道/模型错误语义。

### FR-4：其他页面和调用路径隔离

- `/keys` 配置密钥时的分组选择和模型/渠道能力不得应用该游乐场限制。
- 普通 API、管理端渠道测试、任务插件、其他页面和非游乐场请求不得因该字段改变渠道选择结果。
- 后端必须依据明确的游乐场请求上下文进行限制，不能把过滤永久写入全局渠道能力或全局分组模型缓存。

## 6. 交互与状态

- 开关关闭时显示未选中状态；新建渠道默认未选中。
- 开关开启后保存，重新打开编辑面板应恢复为选中状态。
- 对已有历史渠道没有该字段时，编辑面板显示关闭。
- 游乐场切换分组后重新获取对应模型列表；如果当前模型因过滤后不可用，应沿用现有回退/清空选择逻辑。
- 分组列表加载和现有错误提示保持不变。
- 分组模型为空时，不新增页面级错误；保留分组，模型选择区域按现有空列表表现处理。
- 不新增动画、复杂视觉样式或独立组件，复用现有开关、表单项和选择器。

## 7. 数据与接口约束

- 配置字段使用现有 `channels.settings` 渠道其他设置 JSON 持久化，字段名和 Go/TypeScript 解析逻辑在开发计划中统一确定。
- 默认关闭必须兼容旧数据、空配置和缺少字段的 JSON。
- 不新增数据库列，因此不产生结构迁移；仍需确认现有设置 JSON 的读写和缓存刷新路径能够让新值及时生效。
- 游乐场模型列表接口和实际请求选择逻辑必须共享一致的“允许游乐场调用”判断，避免列表显示与实际调用不一致。
- 模型列表过滤不能通过修改全局 `abilities.enabled` 或删除能力记录实现。

## 8. 权限、安全与兼容性

- 保存配置继续使用现有渠道创建/编辑权限和敏感字段锁定规则。
- 后端不能信任前端隐藏模型；实际游乐场请求必须再次执行服务端过滤。
- 不记录密钥、令牌或其他敏感信息。
- 支持 SQLite、MySQL 和 PostgreSQL；不引入数据库特定 SQL。
- 前端遵循 React、TypeScript、React Hook Form、i18next、现有共享 UI 组件及 Bun 工具链规范。

## 9. 验收标准

1. 新建渠道打开“其他设置”→“渠道额外设置”时可见“禁止游乐场调用”，默认关闭。
2. 开启并保存后重新编辑，开关保持开启；关闭并保存后恢复允许游乐场调用。
3. 游乐场分组中同一模型由一个允许渠道和一个禁止渠道共同提供时，模型仍显示，实际请求不会命中禁止渠道。
4. 某模型只由禁止渠道提供时，该模型不显示在游乐场模型选择栏中。
5. 某分组所有渠道均禁止时，该分组仍显示，但模型列表为空。
6. `/keys` 配置密钥时仍可按原行为看到并使用对应分组；其他非游乐场路径不受影响。
7. 直接构造游乐场请求绕过前端模型列表时，服务端仍不会选择被禁止渠道。
8. 关闭配置或旧渠道缺失配置字段时，既有游乐场行为保持不变。
9. 游乐场模型列表与实际渠道选择在启用、禁用、重试和缓存刷新后保持一致。
10. 由开发者按开发计划执行手动验证，并如实记录前端类型检查、涉及文件 lint、聚焦测试、必要的后端测试和三数据库兼容性验证结果；AI 不编写测试脚本或执行程序验证。
