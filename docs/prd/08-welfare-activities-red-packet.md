## 1. 背景与问题

当前后台“福利活动”管理入口和前台 `/welfare-activities` 页面已经存在，但页面内容仍为空或显示 Coming Soon。需要先设计一个可重复发布的“拼手气红包”活动，供管理员配置并让用户按期数参与领取。

本功能参考常见的拼手气红包体验：管理员配置某一期红包的总额度、份数及单份额度范围，活动到达开抢时间后由用户竞争领取；每个用户最多领取一次，系统在并发请求下仍必须保证总额度和份数不被超发。

## 2. 当前目标

1. 在后台 `/system-settings/site/welfare-activities` 管理拼手气红包活动。
2. 在前台 `/welfare-activities` 展示当前活动、倒计时、抢红包入口和可分页的领取记录。
3. 奖励以用户 API 额度形式发放，并写入钱包流水。
4. 为红包及未来其他福利活动共用一个“福利活动”流水类型。
5. 支持多期红包，期数可作为用户可识别的活动编号，并能查询指定期数的领取历史。

## 3. 已确认的范围

### 3.1 奖励单位

- 红包金额表示用户 API 额度，领取成功后增加用户 `Quota`。
- 额度变更必须沿用现有钱包余额变更和流水记录机制。
- 红包流水使用统一的“福利活动”类型，红包期数和领取记录作为来源信息保存；未来其他福利活动也可以复用该类型。

### 3.2 已确认的页面入口

- 后台入口：`/system-settings/site/welfare-activities`。
- 前台入口：`/welfare-activities`。
- 两个页面当前均为占位实现，本需求允许围绕这两个页面补齐完整功能。

## 4. 用户角色

### 4.1 管理员

- 创建并配置红包期数。
- 设置总额度、红包份数、单份最小额度和计划开抢时间。
- 查看活动状态和领取记录。
- 按确认后的规则分发、结束或切换活动。

### 4.2 普通用户

- 查看当前活动期数、活动状态、剩余份数和剩余额度。
- 在未到开抢时间时查看倒计时。
- 在活动可抢时点击按钮领取一次红包。
- 查看当前期或指定期数的分页领取历史。

## 5. 详细功能需求

### 5.1 后台配置和分发

后台在 `/system-settings/site/welfare-activities` 提供“拼手气红包”管理区，至少支持：

- 创建草稿并填写总额度、红包份数、单份最小额度和计划开抢时间。
- 使用现有额度展示单位进行输入；前端可以显示 USD、CNY、Token 或自定义单位，提交前沿用已有工具换算为内部整数额度，后端再次验证整数与安全范围。默认 `QuotaPerUnit = 500000`，即 500,000 个内部额度单位对应 1 USD。
- 服务端校验总额度和份数为正数，单份最小额度为正整数且不超过 `floor(总额度 / 份数)`；总额度必须至少覆盖每份一个内部 quota 单位，时间必须能解析为中国大陆时间。
- 草稿可以继续编辑或删除。草稿不占用 `issue_no`。
- 管理员点击“分发”时，服务端在一次受保护的操作中校验草稿、分配全局递增期数、生成全部红包金额并锁定配置。分发后配置不可修改。
- 计划时间早于或等于确认时刻时，分发后直接进入进行中；计划时间晚于确认时刻时进入待开抢。
- 已存在一个进行中期时，管理员仍可以创建并分发一个待开抢期；系统最多允许一个进行中期和一个待开抢期。
- 立即开抢的新期分发成功时，已有进行中期立即变为已结束；预约新期则在到点时替换旧期；旧期未领取金额不再发放，已领取记录和已发放额度永久保留。
- 待开抢期可手动结束；进行中期不可手动结束、编辑、恢复或改回草稿，只能由新期替换。已有待开抢期时必须先结束它，才能分发另一新期。
- 后台展示期数、状态、创建人、分发时间、开抢时间、总额度、总份数、剩余额度、剩余份数，以及领取记录入口。

### 5.2 金额生成

分发时一次性生成每个红包的固定额度，之后领取只负责按顺序取出已生成的金额，避免在高并发领取时临时计算出不满足约束的金额。

- 生成结果的总和必须严格等于总额度。
- 先为每份分配保底额度；单份最小额度从 1 个内部 quota 单位开始，确保每份红包都可领取。
- 将扣除保底后的剩余额度使用随机切分点均匀拆分到所有红包，生成结果不设置单份最大额度，因此可能出现较大的幸运红包。
- 生成过程使用 `crypto/rand` 安全随机来源，并再次校验总和及每份正数边界；金额生成失败时整个分发操作回滚，不产生可领取期数。
- 领取顺序由固定红包记录的随机顺序决定，领取金额不因为用户、领取时间或请求顺序而产生额外资格差异。
- 领取最后一份时仍通过数据库事务确认剩余红包，不能依赖缓存计数或前端展示值。

### 5.3 状态推进和后台任务

状态由服务端决定，前端倒计时只用于展示。后台系统任务周期性推进到点的待开抢期：

1. 查找唯一的待开抢期且 `start_at <= now`。
2. 在同一事务中锁定活动状态，结束当前进行中期（如果存在），把待开抢期改为进行中。
3. 使用状态条件和唯一约束保证多实例只能有一个推进结果。
4. 服务重启后继续根据数据库时间推进，任务延迟不会导致提前开放。

领取接口也必须执行同样的时间和状态兜底：未到时间拒绝领取，到点但后台任务尚未运行时允许在事务内完成必要的激活和领取。

### 5.4 前台当前活动

`/welfare-activities` 显示当前活动卡片：

- 活动标题和当前期数，例如“拼手气红包 - 第 68 期”。
- 状态：待开抢、进行中、已抢完或暂无活动。
- 计划开抢时间和中国大陆时间显示。
- 待开抢时显示服务端时间与开抢时间计算出的倒计时，按钮 disabled。
- 进行中且仍有库存时启用“抢红包”按钮；请求发送到响应完成期间继续 disabled。
- 领取成功后显示本人的领取额度和领取时间，并刷新余额、当前活动摘要和历史记录。
- 已领取、已抢完、已结束、未登录或服务端拒绝时显示可理解的状态反馈。
- 前端可以定时刷新当前活动，但不能用本地时间或按钮状态替代服务端校验。

### 5.5 前台领取历史

前台提供按期数查询的分页表格：

- 期数筛选项显示可查询的历史期数，默认选择当前期或最近一期。
- 表格按领取时间倒序分页，至少显示脱敏用户名、领取额度和领取时间。
- 普通用户可以查询所有期数，但不返回邮箱、用户 ID 等敏感字段。
- 无当前活动时仍允许查询历史。

### 5.6 后台领取记录和审计

- 管理员可按期数分页查看完整领取记录，包括用户标识、领取额度、领取时间和记录状态。
- 管理员分发、结束、系统自动激活、自动结束等动作需要记录操作管理员或系统来源，便于审计。
- 领取记录永久保留。第一版不提供导出、批量删除或自动清理。

### 5.7 额度和福利活动流水

领取成功必须将以下写入放在同一事务中：

- 锁定并占用该期的一个红包金额；
- 增加用户 `Quota`，并检查钱包额度上限；
- 创建红包领取记录；
- 创建 `WalletLedgerTypeWelfareActivity` 类型的钱包流水，`SourceType` 标识具体福利活动，`SourceId` 关联红包期数或领取记录；
- 更新缓存只能在事务提交成功后进行。

统一的“福利活动”流水类型用于红包及未来其他福利活动，不为每一种活动新增钱包流水类型。流水需要具备幂等键，重试不能重复增加额度或重复记账。

## 6. 状态、接口和错误契约

### 6.1 活动状态

| 状态 | 含义 | 允许的操作 |
| --- | --- | --- |
| `draft` | 草稿，尚未分发 | 编辑、删除、分发 |
| `scheduled` | 已分发，等待开抢时间 | 查询、结束 |
| `active` | 当前可领取 | 查询、领取；创建新期时可被结束 |
| `finished` | 红包已结束（可能已全部领取，也可能被新一期替换或管理员手动结束） | 查询历史 |

接口返回活动状态、服务器当前时间、开抢时间、剩余份数、剩余额度和当前用户领取结果，保证前端可以在刷新后恢复状态。

### 6.2 用户接口

建议新增以下接口，具体路径以开发计划为准：

- `GET /api/welfare-activities/current`：返回当前进行中期或待开抢期的摘要。
- `GET /api/welfare-activities/issues`：分页返回用户可查询的期数列表。
- `GET /api/welfare-activities/issues/:issue_no/claims`：分页返回指定期数的脱敏领取记录。
- `POST /api/welfare-activities/current/claim`：请求必须携带用户看到的 `issue_no`；以用户和该期号自然幂等，重试不会误领已切换的新一期。

### 6.3 管理接口

建议新增以下接口，全部使用 `AdminAuth`：

- `GET /api/admin/welfare-activities`：分页查询活动期数。
- `POST /api/admin/welfare-activities/drafts`：创建草稿。
- `PUT /api/admin/welfare-activities/drafts/:id`：更新草稿。
- `DELETE /api/admin/welfare-activities/drafts/:id`：删除草稿。
- `POST /api/admin/welfare-activities/drafts/:id/dispatch`：分发草稿。
- `POST /api/admin/welfare-activities/:id/cancel`：仅结束待开抢期；进行中期只能由新期替换。
- `GET /api/admin/welfare-activities/issues/:issue_no/claims`：分页查看完整领取记录。

管理接口不接受客户端直接传入内部余额作为最终依据，金额提交为内部整数，必须由服务端执行范围校验和溢出检查。

## 7. 数据模型和约束

第一版使用四张持久化表：

1. `welfare_activity_issues`：一期红包的配置、状态、期数、剩余资源、时间和审计字段。
2. `welfare_activity_red_packets`：分发时生成的每个固定红包金额、领取状态和领取用户。
3. `welfare_activity_claims`：面向查询和审计的领取记录，保存用户、红包、额度、领取时间和幂等键。

4. `welfare_activity_issue_counters`：固定协调行，事务内分配期号，并保护分发、切期、编辑、结束和领取的互斥。

核心约束：

- `issue_no` 正式分发后全局唯一递增；草稿保存为 NULL，避免唯一索引限制多个草稿；`id` 为数据库主键。
- `(issue_id, user_id)` 唯一，保证同一用户每期最多成功领取一次。
- `(issue_id, packet_index)` 唯一，保证一个红包只能被占用一次。
- 领取幂等键唯一，重复请求返回原领取结果。
- 状态字段、时间字段和剩余计数都由服务端维护，不能由前端覆盖。
- 活动、红包和领取记录加入 `migrateDB` 的 `AutoMigrate` 列表；索引和唯一约束必须能在 SQLite、MySQL 和 PostgreSQL 上工作。

## 8. 并发、失败、回滚和兼容性

- 抢红包入口的按钮 disabled 只负责改善体验，服务端必须防御重复点击、脚本请求和多用户竞争。
- 领取事务应锁定活动/红包行或使用等价的条件更新；涉及用户余额时使用现有 `lockForUpdate(tx)` 方案，SQLite 使用项目已有兼容路径。
- 额度增加、领取记录、红包占用、钱包流水任何一步失败，事务整体失败，不能留下部分成功状态。
- 同一用户并发请求通过唯一约束和幂等查询收敛到一条成功记录；已成功的重试返回原额度。
- 多用户竞争最后一个红包时只允许一个事务成功，其他请求返回“已抢完”或“本期已领取”，不能返回模糊的成功信息。
- 领取成功后才更新缓存；缓存失败不能回滚已提交的数据库事务，也不能让下一次请求多发额度。
- 管理员重复分发、重复结束或任务重复推进必须是幂等操作，不能重复生成期数或红包。
- 数据库字段使用通用 GORM 类型，不使用仅适用于某一种数据库的表达式、锁语法或 JSON 类型。
- 额度计算必须防止整数溢出，并遵守现有钱包上限和 quota 换算规则。

## 9. 验收标准

### 后台

- 可以创建、编辑、删除草稿，并能看到明确的金额、份数和时间校验错误。
- 分发后获得唯一的“第 N 期”，金额配置锁定，生成红包总额严格正确。
- 未来时间进入待开抢，过去或当前时间可立即领取。
- 已有进行中期时可以排队一个待开抢期；新期到点后旧期立即结束且不会再发放未领取金额。
- 草稿、待开抢、进行中和已结束状态与允许操作一致。
- 后台可以分页查看完整领取记录和管理员操作来源。

### 前台

- 页面可显示当前期数、状态、时间、倒计时、剩余份数和剩余额度。
- 未到时间或无库存时按钮 disabled，到点后可以领取；请求中不能重复提交。
- 成功领取后用户额度增加一次，页面显示本人领取结果。
- 同一用户重复领取返回原结果或明确的已领取状态，不会增加第二次额度。
- 高并发领取最后一个红包时总成功数和总发放额度不超过配置值。
- 历史记录可以按期数筛选和分页，普通用户看到脱敏信息，管理员看到完整信息。
- 页面和接口覆盖现有七种前端语言，所有用户可见文本使用 i18n。

### 数据库和恢复

- SQLite、MySQL、PostgreSQL 均能完成建表、重复启动迁移和核心领取事务。
- 服务重启后待开抢期仍会在正确时间激活；后台任务重复执行不会重复发放。
- 任何额度、红包占用、领取记录或流水写入失败都不会留下部分成功。

## 10. 设计约束

- 余额变更必须复用现有额度上限和钱包流水机制，不能直接修改用户额度而绕过流水。
- 红包领取需要具备幂等键，避免重复请求或重试造成重复发放。
- 所有金额、份数、时间和状态转换都必须在服务端再次校验，不能依赖前端 disabled 或倒计时。
- 需要继续支持 SQLite、MySQL 和 PostgreSQL。
- 前端文案需要支持现有七种语言，并复用项目已有表单、表格、分页、按钮、状态和错误处理组件。
- 文档阶段不修改业务代码，不启动开发服务器、数据库、容器或其他持久服务。

## 13. 首版落地说明（2026-10-13）

- 每期最多 10,000 份；单份最小值为一个内部额度单位，默认 500,000 单位对应 1 USD。
- `current` 返回 `server_time`、`issue` 和 `upcoming`：优先展示当前可抢期，同时展示下一预约期；没有可抢期则展示预约期，均无则返回空。
- 金额在协调锁之外预生成；分发事务内重新核对草稿版本的全部配置，校验未变化后才写入并分配期号。
- 领取事务第一条 SQL 更新固定协调行，随后统一检查到点替换、指定期号、用户状态、期内唯一领取和钱包上限。SQLite 由先写后读避免读锁升级；其他数据库复用 `lockForUpdate`。
- 开抢边界以持有协调锁时的服务器时间为判定点；先取得锁且在边界之前判定的旧期领取，与新期切换保持事务顺序。
- 红包占用、用户额度增量、领取记录、福利活动流水和剩余计数在同一个主库事务中提交。已提交重试返回原领取，包括已结束或被替换的旧期。
- 领取接口固定限制单用户 5 秒内最多 3 次请求，复用 Redis/内存用户限流器；数据库领取事务最多等待 10 秒。超时或失败不自动重复发钱，可按原期号重试确认结果。
- 后台任务按既有 15 秒调度粒度检查到点期；没有到点期不创建空跑任务。当前活动查询和领取都提供到点兜底。
- 前台倒计时以服务器时间和浏览器单调时钟计算，定时刷新为 10 秒，不逐秒请求；到点可提交预约期号，由服务端决定是否激活并领取。
- 普通管理员仅开放福利管理的指定设置路径，不扩大对其他系统设置的权限；该页面不读取仅超级管理员可访问的全局选项。
- 尚未执行测试、构建、lint、类型检查、i18n 同步检查或三数据库实机验证。此实现以安全串行化优先，吞吐量受数据库和事务耗时限制，不能据代码静态实现承诺生产并发容量。
