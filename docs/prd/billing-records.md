# 账单记录页面 PRD 与开发设计

> 状态：已确认，已完成首版开发
>
> 编写日期：2026-09-13
>
> 关联入口：前台个人中心 → 账单记录
>
> 页面路由：`/billing-records`

## 1. 文档目的

本文档用于统一“账单记录”页面的产品口径、数据边界和实现方案，并作为首版开发与验收依据。

## 2. 背景与目标

当前项目已有钱包充值记录弹窗，主要基于 `TopUp` 订单展示充值记录；同时已有 `SubscriptionOrder` 订阅订单、日志记录和用户额度变更逻辑，但这些数据尚未统一为用户可查询的账单视图，也没有稳定记录余额变更前后的快照。

本功能目标：

1. 在个人中心提供统一的“账单记录”页面。
2. 通过顶部 Tabs 区分“消费记录”和“余额流水”。
3. 为用户提供可分页、可筛选的支付订单记录。
4. 为所有会导致钱包余额变化的非模型调用行为建立可追溯流水。
5. 保持常规模型调用消费与现有使用日志的职责边界，不在余额流水中重复记录。

## 3. 页面范围与布局

### 3.1 页面结构

页面整体布局参考 `/models/metadata`：

- 使用现有 Section 页面布局。
- 页面标题为“账单记录”。
- 标题区域下方为 Tabs。
- Tabs 下方为当前 Tab 独立的查询条件、表格和分页区域。
- 两个 Tab 的查询条件、表格数据和分页状态互相隔离；切换 Tab 时不应把一个 Tab 的筛选条件带到另一个 Tab。
- 桌面端使用表格展示；窄屏下沿用项目现有数据表的横向滚动或响应式降级方式，不新增一套重复的表格组件。

### 3.2 Tabs

| Tab | 说明 |
| --- | --- |
| 消费记录 | 展示用户实际发起支付的订单，包括余额充值、外部支付购买订阅等支付订单。 |
| 余额流水 | 展示导致用户钱包余额增减的业务记录，但排除常规模型调用消费。 |

默认打开“消费记录”。Tab 切换不触发页面跳转；当前选中的 Tab 可以使用本地页面状态维护，除非实现时项目现有路由约定要求同步到 search 参数。

## 4. 消费记录

### 4.1 业务边界

消费记录只包含用户产生实际支付行为的支付订单，至少包括：

- 通过微信支付、支付宝、Stripe、Creem、Waffo 等支付渠道购买余额。
- 通过微信支付、支付宝、Stripe、Creem、Waffo 等支付渠道购买订阅。
- 后续新增的、确实产生外部支付金额的用户订单。

默认不纳入消费记录的行为：

- 兑换码兑换。
- 管理员直接补单或管理员直接调整额度。
- 邀请奖励、佣金返利、系统赠送额度。
- 使用钱包余额购买订阅（没有新的外部支付金额；其余额扣减进入余额流水）。
- 常规模型调用产生的消费（属于使用日志，不属于支付订单）。

“消费记录”中的订单即使支付失败、待支付或已过期，也应保留，只要该订单已被创建并属于当前用户；列表状态以订单最终状态为准。

### 4.2 表格字段

| 字段 | 展示规则 | 数据要求 |
| --- | --- | --- |
| 账单单号 | 展示统一订单号，支持复制和关键词查询 | 充值订单使用 `TopUp.TradeNo`；订阅订单使用 `SubscriptionOrder.TradeNo`；统一接口返回 `bill_no` |
| 消费类型 | 例如“余额充值”“订阅购买” | 后端返回稳定类型枚举，前端通过 i18n 展示，不直接依赖数据库描述文本 |
| 付款方式 | 例如微信支付、支付宝、Stripe、余额 | 由支付方式/支付提供方统一归一化后展示；不能把内部 provider 原值直接作为用户文案 |
| 实际支付 | 用户实际支付金额 | 使用订单 `Money`；保留金额精度，按项目现有货币格式化规则展示，并带站点货币符号/单位 |
| 状态 | 成功、待支付、已过期、失败、已取消等 | 后端返回稳定状态枚举；未知状态需要有安全降级文案 |
| 创建时间 | 按站点时区格式化 | 使用订单创建时间；排序默认按创建时间倒序，时间相同按稳定唯一字段倒序 |

“实际支付”与到账额度是两个不同概念：消费记录显示支付金额，不显示充值 quota；充值到账额度在余额流水中体现。

### 4.3 查询条件

建议统一提供以下条件：

- 关键词：账单单号。
- 消费类型：全部、余额充值、订阅购买及未来扩展类型。
- 付款方式：全部及当前系统已启用的支付方式。
- 状态：全部、成功、待支付、已过期、失败、已取消等。

- 每页条数：沿用现有列表规则，默认 10 条，支持 20/50/100 条。

查询条件变更后重置到第 1 页。查询、排序和分页均在后端完成，避免只在前端截取数据。

### 4.4 数据来源与接口设计

现有数据来源：

- 余额充值：`model.TopUp`，当前已有用户接口 `GET /api/user/topup/self`。
- 订阅支付：`model.SubscriptionOrder`，当前已有订阅订单数据模型。
- 钱包余额购买订阅：同样会形成订阅订单，但默认不进入“实际支付订单”列表，具体口径见待确认问题。

建议新增面向当前登录用户的统一查询接口，而不是让前端并行请求多个订单接口并自行合并：

```text
GET /api/user/billing-records/consumption
GET /api/user/billing-records/balance-ledger
```

建议请求参数：

```text
page
page_size
keyword
type
payment_method
status
```

建议响应保持项目现有分页响应结构：

```text
{
  success: true,
  data: {
    items: [...],
    total: 0,
    page: 1,
    page_size: 10
  }
}
```

统一消费记录项建议至少包含：

```text
{
  id,
  bill_no,
  type,
  payment_method,
  amount,
  currency,
  status,
  create_time
}
```

其中 `id` 只能作为稳定排序/前端 key 使用，用户可见单号使用 `bill_no`。

## 5. 余额流水

### 5.1 业务边界

余额流水只记录会导致用户钱包余额发生变化的业务事件，包括但不限于：

- 支付充值到账。
- 兑换码兑换到账。
- 管理员补单到账。
- 使用钱包余额购买订阅产生的扣减。
- 管理员增加、扣减或覆盖用户余额。
- 邀请奖励到账。
- 佣金返利到账。
- 系统赠送、签到、补发等导致钱包余额变化的行为。
- 后续新增的其他钱包余额增减行为。

明确排除：

- 常规调用大模型产生的消费；该行为继续通过使用日志体现，不在余额流水重复展示。
- 仅改变订阅额度使用量、但不改变钱包余额的模型调用消费。
- 仅创建支付订单但尚未导致余额变化的待支付订单。

余额流水必须以“钱包余额实际变更成功”为记录前提；失败的业务操作不得产生成功流水。

### 5.2 表格字段

| 字段 | 展示规则 | 数据要求 |
| --- | --- | --- |
| 流水单号 | 展示统一流水号，支持复制和关键词查询 | 新增流水统一编号；如有来源订单号，另外保留来源引用，不混用展示字段 |
| 流水类型 | 例如充值、兑换码、补单、订阅购买、管理员调整、邀请奖励、佣金返利 | 后端返回稳定类型枚举，前端通过 i18n 展示 |
| 变动额度 | 增加显示正数，扣减显示负数 | 单位为系统钱包 quota；使用项目现有额度格式化规则；增加/扣减需要有可访问的方向语义，颜色只能作为辅助 |
| 变动前余额 | 本次变更前的钱包 quota | 必须来自同一事务内的余额快照 |
| 变动后余额 | 本次变更后的钱包 quota | 必须来自同一事务内的余额快照 |
| 创建时间 | 按站点时区格式化 | 使用流水创建时间；默认按创建时间倒序，时间相同按稳定唯一字段倒序 |

前端展示单位以现有钱包余额单位配置为准：如果站点余额使用 `$` 展示，则“变动额度”“变动前余额”“变动后余额”均使用 `$` 展示；如果站点余额使用 tokens/quota 展示，则使用对应的额度单位展示。后端仍保存整数 quota 原值，前端复用项目现有余额格式化工具完成展示，不新增另一套换算规则。

### 5.3 查询条件

建议提供以下条件：

- 关键词：流水单号、来源订单号（如果接口支持来源单号搜索）。
- 流水类型：全部、充值、兑换码、补单、订阅购买、管理员调整、邀请奖励、佣金返利、系统赠送等。
- 余额变动方向：全部、增加、扣减。

- 每页条数：默认 10 条，支持 20/50/100 条。

查询条件变更后重置到第 1 页；分页、排序和过滤由后端执行。

### 5.4 统一流水数据模型

现有 `User` 只保存当前余额，现有日志/业务记录也不能稳定覆盖所有余额变动前后快照。因此建议新增独立的钱包流水表（名称可在实现阶段按项目命名规范确定），而不是依赖日志表反向解析：

```text
WalletLedger
- id                 主键
- user_id            用户 ID，建立索引
- ledger_no          对用户展示的唯一流水号，建立唯一索引
- type               稳定流水类型枚举，建立索引
- delta_quota        余额变动量，正数为增加，负数为扣减
- balance_before    变动前余额
- balance_after     变动后余额
- source_type        来源业务类型
- source_id         来源业务 ID/订单号，可为空
- idempotency_key   幂等键，建立唯一约束
- created_at         创建时间，建立用户+时间复合索引
```

设计约束：

1. `delta_quota`、`balance_before`、`balance_after` 使用足够的整数类型，禁止用浮点数。
2. `balance_after = balance_before + delta_quota`，写入前后校验该不变量。
3. 钱包余额更新与流水插入必须处于同一个数据库事务中。
4. 对同一用户的余额更新需要使用项目现有跨数据库兼容的行锁/原子更新策略，避免并发下快照错误。
5. 同一业务事件只能插入一条流水；重复回调、重复请求、重试不能重复记账。
6. 流水记录原则上不可更新、不可删除；如未来支持冲正，应新增一条反向流水并保留原流水。
7. 充值、兑换码、管理员调整、邀请奖励/佣金等入口均应在实际余额变更的公共业务路径中落流水，避免只改某一条调用链。
8. 正常模型调用消费不应调用该流水写入逻辑。

### 5.5 历史数据兼容策略

当前历史数据存在以下限制：

- 历史充值订单可从 `TopUp` 读取，但不一定能还原统一消费记录中的所有类型和最终支付信息。
- 历史订阅订单可从 `SubscriptionOrder` 读取，但需要确认是否纳入钱包/消费记录，以及其支付方式和状态映射。
- 历史日志/用户余额变更未必保存余额变动前后快照和统一流水号。
- 仅依靠当前余额无法可靠反推出每一笔历史余额变动的前后余额。

因此建议采用分阶段策略：

1. 消费记录：对可从现有订单表可靠读取的历史充值订单和订阅支付订单提供查询；缺失字段按明确的兼容映射展示，不伪造数据。
2. 余额流水：新版本上线后所有余额变更写入新流水表。
3. 历史余额流水：若没有可靠的历史快照，则不生成虚假的前后余额；是否执行可标记为“未知”的历史补录，需要产品确认。
4. 若决定补录历史流水，必须设计一次性、可重入的迁移/回填标记，并明确无法还原字段的展示规则。

## 6. 权限与数据隔离

- 页面仅允许已登录用户访问。
- 用户接口必须由服务端从认证上下文取得 `user_id`，不得信任前端传入的用户 ID。
- 查询必须强制限定当前用户，只能返回自己的消费记录和余额流水。
- 不复用管理员全量查询接口作为前台接口，避免越权和响应字段泄漏。
- 不返回支付 provider 原始回调 payload、敏感支付信息或管理员内部审计信息。
- 账单号、流水号仅用于展示和查询，不应被视为授权凭证。

## 7. 一致性、幂等与失败处理

### 7.1 支付订单

- 充值支付回调和订阅支付回调沿用各自现有的订单状态机和幂等机制。
- 统一消费查询只读订单最终持久化状态，不在查询接口中重新推断支付结果。
- 不因前端查询失败、分页重试或重复打开页面产生任何写操作。

### 7.2 余额流水

- 余额更新成功但流水写入失败时，整个事务必须回滚；不能留下无法追溯的余额变化。
- 流水写入成功但缓存同步失败时，按现有缓存一致性策略处理，并保证数据库记录为最终事实来源。
- 重复支付回调、重复兑换、重复管理员操作重试必须通过幂等键避免重复流水。
- 余额不足、额度上限、业务校验失败时不得写入成功流水。

## 8. 前端实现设计（确认后开发）

### 8.1 组件复用

开发前必须复用现有能力：

- 参考 `/models/metadata` 的页面、Tabs、查询区和表格布局。
- 检查并优先复用 `DataTable`、分页、空状态、加载状态、错误状态、复制按钮、状态徽章、金额和 quota 格式化工具。
- 充值历史弹窗 `web/src/features/wallet/components/dialogs/billing-history-dialog.tsx` 仅作为字段和状态映射参考；不能因为布局不同而复制其请求/分页逻辑。
- 新增通用能力前，需要先记录现有组件缺失的具体能力。

### 8.2 i18n

所有新增页面文案、Tab、字段名、筛选项、状态和空状态文案均通过 `react-i18next` 的 `t()` 展示，并同步支持项目现有语言：en、zh、zh-TW、fr、ru、ja、vi。不得在组件中硬编码仅中文文本作为用户可见文案。

### 8.3 加载、空状态与错误状态

- 首次请求显示现有项目风格的 loading 状态。
- 无数据时显示可翻译的空状态，不显示错误。
- 请求失败时使用项目统一错误处理和路由/页面错误承接方式。
- 切换 Tab 或筛选条件时避免旧数据误显示为新查询结果；必要时保留加载态或请求序列保护。

## 9. 后端与数据库开发设计（确认后开发）

### 9.1 API

- 新增两个仅面向当前用户的分页 GET 接口，或在项目已有路由规范下使用等价命名。
- 接口返回稳定枚举和前端所需展示字段，前端不拼接多个订单表、不解析日志内容。
- 参数校验、分页上限、关键词长度和类型枚举校验由后端完成。
- 数据库查询需支持 SQLite、MySQL >= 5.7.8、PostgreSQL >= 9.6。

### 9.2 数据库

- 新增余额流水表需要使用 GORM 模型与跨数据库兼容迁移。
- 迁移必须支持新库初始化和已有库升级，重复启动保持幂等。
- 为用户+创建时间、用户+流水号、幂等键建立必要索引/唯一约束。
- 不使用数据库特有的 JSON、函数、锁语法或自动增量写法替代 GORM 的跨库能力。
- 如选择历史回填，必须单独设计可重入迁移并覆盖现有数据兼容验证。

### 9.3 测试与验证

至少覆盖：

- 消费记录只返回当前用户订单。
- 充值订单、订阅支付订单的类型/付款方式/状态/金额映射。
- 待支付、成功、已过期、失败订单均可按状态筛选。
- 余额流水的增加、扣减、前后余额不变量。
- 充值、兑换码、管理员调整、余额购买订阅、邀请奖励、佣金返利等来源的流水类型。
- 常规模型调用消费不会进入余额流水。
- 重复回调/重试不产生重复流水。
- 时间、关键词、类型、方向、分页查询正确。
- SQLite、MySQL、PostgreSQL 的迁移和关键查询兼容。
- 前端 Tabs、筛选、表格、空状态、错误状态、分页和移动端可用性。

- [ ] 充值、兑换码、补单、管理员调整、余额购买订阅、邀请奖励、佣金返利等实际余额变化可追溯。
- [ ] 常规模型调用消费不会展示在余额流水。
- [ ] 每一条新增流水的前后余额和变动额度满足一致性不变量。
- [ ] 重复处理不会重复扣款、入账或写入流水。
- [ ] 任何用户不能查询其他用户的记录。

## 11. 已确认决策

### 11.1 订阅购买在两个 Tab 中的归属

已确认采用严格的余额变化口径：

- 使用钱包余额购买订阅：进入“余额流水”，作为钱包余额扣减记录。
- 通过微信、支付宝、Stripe、Creem、Waffo 等外部支付购买订阅：进入“消费记录”，不进入“余额流水”。
- “余额流水”不展示余额未发生变化的外部支付订阅事件。

## 12. 已确认决策

### 12.1 查询条件

已确认按 PRD 建议提供查询条件：

- 消费记录：关键词、消费类型、付款方式、状态、每页条数。
- 余额流水：关键词、流水类型、余额变动方向、每页条数。
- 查询条件变更后重置到第 1 页。
- 查询、筛选、排序和分页均由后端完成。

## 13. 已确认决策

### 13.1 历史余额流水

已确认采用“从新版本上线后开始记录”的策略：

- 历史充值订单、历史订阅支付订单根据现有订单表展示在“消费记录”。
- 历史余额流水不强行补录，不根据当前余额反推历史变动前后余额。
- 新版本上线后，所有符合范围的余额变更写入统一流水表。
- 不伪造无法可靠还原的历史流水和余额快照。

## 14. 已确认决策

### 14.1 余额字段展示单位

已确认“变动额度”“变动前余额”“变动后余额”以现有钱包余额单位配置为准：

- 如果站点余额使用 `$` 展示，则三个余额字段均使用 `$` 展示。
- 如果站点余额使用 tokens/quota 展示，则三个余额字段使用对应的额度单位展示。
- 后端仍保存整数 quota 原值，前端复用项目现有余额格式化工具完成展示，不新增另一套换算规则。
- “消费记录”的“实际支付”仍使用订单支付金额和货币格式展示，两者不混淆。
## 15. 已确认决策

### 15.1 余额流水编号

已确认新增统一流水号：

- 每条余额流水生成独立且唯一的 `ledger_no`，作为用户可见的流水单号。
- 来源订单号、兑换码记录 ID、管理员操作 ID 等保留在来源字段中，作为辅助追踪信息。
- 流水号不复用支付订单号，也不直接把数据库自增 ID 作为用户展示编号。

### 15.2 管理员补单归属

根据原始需求确认：

- 管理员补单如果实际导致用户钱包余额增加，进入“余额流水”。
- 管理员补单不属于“消费记录”，因为它不是用户实际支付行为。

## 16. 已确认决策

### 16.1 退款、冲正与拒付

已确认当前版本暂不支持退款、冲正、拒付等面向用户的反向支付记录：

- 当前项目暂无面向用户的支付退款流程。
- V1 仅实现现有充值支付、外部支付订阅订单和余额变更流水。
- 未来若新增退款或冲正能力，应设计为新的反向订单状态或反向余额流水，不修改原始流水记录。
