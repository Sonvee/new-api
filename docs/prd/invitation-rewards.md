# 邀请奖励与佣金返利机制

## 1. 文档目的

本文档记录邀请奖励机制重写后的产品需求、业务规则、配置项和实现约束，作为后续开发、测试和维护的统一依据。

## 2. 页面与入口

### 管理端

- 路径：`/system-settings/billing/affiliate-rewards`
- 所属菜单：系统设置 → 计费与支付 → 邀请奖励
- 邀请奖励页面与 `/system-settings/billing/quota` 共用邀请者奖励、受邀者奖励配置。两处使用相同配置 key，任一页面修改后另一处读取到的值保持一致。

### 前台

- 路径：`/affiliate-rewards`
- 入口受侧边栏模块配置控制，归属于“个人中心”。

前台邀请奖励页面的首行统计展示：

- 总邀请人数：读取邀请者累计邀请人数。
- 有效邀请人数：读取已达到邀请激活阈值的邀请人数。
- 邀请奖励：读取直接到账的固定邀请奖励累计额度。
- 佣金返还：读取支付充值产生并直接到账的佣金累计额度。

## 3. 核心概念

### 3.1 已邀请用户

用户通过邀请链接注册后，即记录邀请关系并计入邀请者的已邀请用户数量，但此时不代表已经激活，也不会发放固定邀请奖励或产生佣金。

### 3.2 有效邀请

受邀用户的当前账户余额首次达到邀请激活阈值后，邀请关系成为有效邀请。

- 判断基数是用户当前余额，而不是累计充值金额。
- 用户消费导致余额下降后，不会撤销已经完成的激活。
- 已激活关系永久保持有效。
- 同一邀请关系只能完成一次激活和一次固定奖励发放。

### 3.3 邀请激活阈值

配置 key：`InvitationActivationThreshold`

- 默认值：`10000000` quota，对应当前 `QuotaPerUnit=500000` 时的 `$20`。
- 取值范围：`0` 至系统允许的钱包额度上限。
- 设置为 `0` 时，受邀用户注册即视为有效邀请。
- 设置为大于 `0` 时，只有当前余额达到阈值才激活。

示例：阈值为 `$20`，用户先充值 `$10`，再消费 `$5`，随后充值 `$10`，当前余额为 `$15`，仍不能激活。

## 4. 奖励规则

### 4.1 邀请者奖励与受邀者奖励

配置项：

- `QuotaForInviter`：邀请者奖励
- `QuotaForInvitee`：受邀者奖励

受邀用户首次达到激活条件时：

1. 邀请者奖励直接增加到邀请者余额。
2. 受邀者奖励直接增加到受邀者余额。
3. 两笔奖励均计入邀请奖励历史额度。
4. 不再进入待划转额度，也不需要用户手动操作。

上述两个配置项继续沿用原有配置，不新增重复字段。

### 4.2 佣金比率

配置 key：`CommissionRate`

- UI 名称：佣金比率(%)
- 默认值：`5`
- 取值范围：`0` 至 `100`。
- 佣金计算公式：`实际到账额度 × 佣金比率 ÷ 100`。

佣金只适用于受邀用户已经激活之后发生的支付充值，并直接增加到邀请者余额。

## 5. 支付与佣金处理顺序

佣金只由受邀用户通过支付渠道完成的充值产生，按该笔充值实际到账的 quota 计算，不考虑汇率。

- 兑换码：可以触发有效邀请，但不产生佣金。
- 管理员直接调整额度：可以触发有效邀请，但不产生佣金。
- 签到、系统补发等非支付额度增加：可以触发有效邀请，但不产生佣金。
- Stripe、易支付、Creem、Waffo 等支付充值：可以触发有效邀请；如果该受邀用户在本笔处理后达到激活条件，则本笔实际到账额度可以产生佣金。

### 示例

阈值 `$20`、佣金比率 `5%`、邀请者奖励 `$1`、受邀者奖励 `$2`：

1. 受邀用户充值 `$10`：余额未达标，不激活，不发固定奖励，不产生佣金。
2. 受邀用户再次支付充值并实际到账 `$10`：余额达到 `$20`，关系激活；邀请者获得 `$1` 固定奖励，受邀者获得 `$2` 固定奖励，同时本笔 `$10` 产生 `$0.50` 佣金。
3. 如果受邀用户首次一次性实际到账 `$20`，则关系立即激活，且本笔按 `$20 × 5% = $1` 计算佣金。
4. 激活后的后续每一笔支付充值，都按该笔实际到账额度计算佣金。

## 6. 直接到账与幂等

- 固定奖励和佣金均直接写入用户余额，不提供“手动划转”流程。
- 处理支付回调时必须保持订单幂等，重复回调不能重复增加充值额度、固定奖励或佣金。
- 邀请关系激活必须保持幂等，重复执行不能重复发放固定奖励。
- 邀请者有效邀请数量在首次激活时增加一次。

## 7. 退款范围

当前项目没有面向用户或管理员的支付订单退款功能。项目中已有的 refund 逻辑仅用于请求预扣费、异步任务或任务计费失败后的额度返还，不属于支付订单退款。

因此本机制暂不设计支付退款、拒付、佣金扣回或奖励回滚。支付充值成功并发放佣金后，不再进行后续退款反向处理。

## 8. 历史数据兼容

为尽量减少对原有邀请逻辑的改动：

- 保留原有邀请者奖励、受邀者奖励配置 key。
- 历史待划转邀请额度 `AffQuota` 在迁移时一次性转入用户余额并清空旧字段，避免历史奖励永久停留在待划转状态。
- 已存在的历史邀请关系按兼容策略视为已激活，并不重复发放历史固定奖励。
- 旧版本已记录的 `AffHistoryQuota` 在首次升级时归入固定邀请奖励统计；新产生的佣金单独记录到佣金统计字段。
- 新注册的邀请关系使用有效邀请和激活阈值规则。
- `AffHistoryQuota` 继续保留作为邀请相关额度历史总计；前台统计另外使用固定邀请奖励累计额度和佣金累计额度字段，避免两类数据混合展示。

迁移必须具备幂等性，重复启动不能重复转移历史额度或重复增加有效邀请数量。

## 9. 验收要点

- 管理端页面可以读取和保存四项配置，邀请者奖励与受邀者奖励和 quota 页面同步。
- 中文环境不显示新增配置项的英文 fallback。
- 阈值未达到时不发固定奖励、不增加有效邀请数、不产生佣金。
- 支付充值达标时，固定奖励和触发激活的本笔佣金均正确直接到账。
- 达标前的支付充值不产生佣金；激活后的后续支付充值按实际到账额度产生佣金。
- 非支付额度增加可以触发激活，但不产生佣金。
- 阈值为 `0` 时注册完成即可激活，固定奖励只发放一次。
- 用户余额下降不会取消既有激活状态。
- 重复支付回调和重复激活处理不会重复记账。
- 不新增支付退款相关流程。
