- 状态：已实现，待开发者手动验证
- 关联计划：[`docs/plans/06-repeatable-legacy-data-migration-plan.md`](../plans/06-repeatable-legacy-data-migration-plan.md)

## 1. 背景与问题

当前已将旧项目 PostgreSQL 数据迁移到新项目。数据库可以启动且主要业务数据仍在，但新旧版本在模型字段、API 返回字段、计算字段和新增业务状态上存在差异。已确认的示例是：旧接口的 `invite_count` 由 `users.inviter_id` 关系动态统计，新接口读取持久化字段 `users.aff_count`；升级过程未完成对应数据回填，导致新版页面显示错误。

用户预计后续还会重复执行旧项目到新项目的数据迁移，因此需要一套完整、可重复、可审计、可回滚的迁移方案，而不是继续逐字段执行临时 SQL。

## 2. 已确认目标

1. 以旧项目源码和旧数据库结构为迁移来源，以新项目源码和新数据库结构为迁移目标。
2. 对比数据库模型、GORM 字段映射、启动迁移、控制器/DTO/API 输出和业务计算逻辑，不能仅根据字段名称猜测映射关系。
3. 形成覆盖迁移前检查、备份、dry-run、正式迁移、迁移后校验和回滚的完整流程。
4. 迁移必须可重复执行，并避免重复计数、重复发放奖励、重复记账或覆盖新系统已产生的数据。
5. 输出明确的字段/实体迁移矩阵，区分：同名同义、字段改名、计算字段持久化、新增字段、废弃字段和需要人工决策的字段。
6. 将已经手工处理的 `aff_count` 回填纳入统一迁移设计，避免未来再次人工执行临时 SQL。

## 3. 已确认事实

### 3.1 数据与源码

- 旧、新数据库均为 PostgreSQL 15.19 导出的 schema。
- 新数据库在旧 schema 基础上新增了认证、审计、会计、任务插件、会话和钱包流水等表。
- `users` 表新版本新增：`access_token_created_at`、`aff_reward_quota`、`aff_commission_quota`、`aff_valid_count`、`affiliate_activated`、`auth_version`。
- 旧、新 `users` 表均已有：`aff_count`、`aff_quota`、`aff_history`、`inviter_id`。
- 旧接口字段不一定对应数据库列；例如 `invite_count` 是根据 `inviter_id` 动态统计的 API 字段。

### 3.2 安全边界

- 不直接修改或覆盖旧项目源码。
- 正式迁移前必须有可恢复的数据库备份。
- 未确认业务语义前不得按相似字段名直接复制数据。
- 涉及额度、邀请奖励、佣金、订阅、钱包或会计的数据迁移必须防止重复入账和负数/溢出。
- 迁移失败不得让数据库停留在部分完成且无法识别的状态。

## 4. 暂定范围

- 用户、邀请关系、邀请奖励、佣金和余额/额度字段。
- 令牌、渠道、订阅、充值、兑换、任务、日志、系统配置等旧数据的兼容性检查。
- 新增表的初始化、回填或明确保持为空的规则。
- 新旧 API 字段语义差异与页面依赖的数据契约。
- 迁移版本标记、幂等性、执行记录、校验和回滚。

## 5. 源码对比初步结论

- 旧源码的 `model.User` 将 `invite_count`、`effective_invite_count`、`total_invitation_reward`、`total_commission_reward` 定义为 `gorm:"-:all"` 的计算字段。
- 旧源码的 `loadUserInviteFinance` 从 `invite_relations`、`invite_rewards` 和 `recharge_commissions` 汇总这些字段。
- 新源码将 `aff_reward_quota`、`aff_commission_quota`、`aff_valid_count`、`affiliate_activated` 等作为持久化字段，并通过 `migrateAffiliateRewardHistory` 做部分历史回填。
- 当前新源码的启动迁移没有把 `invite_relations` 的关系数量回填到 `users.aff_count`；本次手工修复的 `aff_count` 回填属于应纳入独立迁移命令的规则。
- 因此，字段迁移必须以业务明细表和源码计算逻辑为权威来源，不能仅按 JSON 字段名称或 GORM 字段名称做一对一复制。

## 5. 非目标

- 不在需求和计划阶段修改业务代码或生产数据库。
- 不通过删除旧数据来规避兼容问题。
- 不把新系统运行后产生的数据无条件覆盖成旧系统数据。
- 不把旧项目中的全部定制代码自动合并到新项目；本任务聚焦数据迁移与兼容。

- 2026-09-18：需要可重复使用的完整迁移方案，而非一次性临时 SQL。
- 2026-09-18：迁移能力采用仓库内独立迁移命令，显式执行并提供检查、预览、应用、校验流程；不绑定应用启动自动执行。
- 2026-09-18：迁移命令本次只支持 PostgreSQL，不扩展 SQLite 或 MySQL；本次迁移服务于用户实际使用的 PostgreSQL 部署，不要求为迁移工具增加未使用的数据库方言支持。
- 2026-09-18：迁移命令只面向全新目标数据库，不负责与目标库已有业务数据进行合并。
- 2026-09-18：迁移流程先将旧数据库恢复到目标 PostgreSQL，再在目标库内执行数据兼容迁移，不要求命令同时连接旧库和新库。
- 2026-09-18：独立迁移命令不重复负责表结构迁移；执行前检查新版本所需 schema，表结构由新项目既有 schema migration 完成。
- 2026-09-18：迁移数据变更在一个 PostgreSQL 事务中执行；任一步骤失败时整体回滚，不留下部分完成状态。
- 2026-09-18：正式迁移前必须停止 new-api 应用容器，迁移命令不负责自动停止或启动容器。
- 2026-09-18：迁移范围包含所有业务表和日志表；日志、审计、任务和临时数据也纳入迁移设计，不默认跳过。
- 2026-09-18：保留密码、API Token、Passkey 等长期凭证；使登录会话和临时认证流程失效，不迁移可复用的临时认证状态。
- 2026-09-18：统计值、余额和奖励等可由明细重建的派生字段，优先依据关系、明细记录和流水重新计算，不直接复制旧版本缓存值。
- 2026-09-18：本次工具只支持当前保存的老源码到当前新源码这一对固定版本，不承担所有历史版本兼容。
- 2026-09-18：迁移实现采用仓库内独立的 `cmd/data-migrate/` 工具目录，与主服务启动逻辑隔离；不制作前端迁移页面，不干扰原有业务代码。
- 2026-09-18：禁止 AI 编写测试脚本或执行测试验证；实现完成后由开发者本人按照计划手动验证，AI 只提供验证步骤和结果记录模板。
