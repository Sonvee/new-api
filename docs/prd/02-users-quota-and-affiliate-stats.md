## 1. 背景与问题

管理员在 `/users` 页面查看用户列表时，当前邀请信息只展示邀请人数和邀请收益，没有单独展示佣金累计值。管理员还需要在用户筛选条件栏附近快速了解全站额度规模和当前剩余额度，但目前没有对应的统计接口和页面展示。

## 2. 目标与非目标

### 2.1 目标

- 在用户列表“邀请信息”列追加激活人数和佣金信息，保持现有邀请人数、收益和邀请人 ID 展示不变。
- 新增一个仅管理员可调用的 `GET` 统计接口，返回全站所有用户的：
  - 全站总额度：所有用户 `quota + used_quota` 的总和；
  - 全站剩余额度：所有用户 `quota` 的总和。
- 在 `/users` 页面条件选择栏中“角色”筛选项右侧，展示与角色筛选项等高的统计盒子，内容包含全站总额度和全站剩余额度，并使用竖分割线分隔。
- 所有新增用户可见文案支持现有前端 i18n。

### 2.2 非目标

- 不调整额度、消费、邀请奖励或佣金的业务计算规则。
- 不新增数据库表、字段、定时汇总任务或独立统计缓存。
- 不改变普通用户或非管理员访问权限。
- 不提供按用户、角色、状态或用户组过滤后的额度统计；统计范围始终为全站所有用户。

## 3. 用户与场景

- 使用者：管理员（当前 `/users` 页面已经限制管理员访问）。
- 前置条件：管理员已登录，主数据库可用，用户列表页面可以正常加载。
- 主要路径：管理员打开 `/users`，在用户筛选栏查看全站额度统计，并在列表邀请信息列查看每个用户的佣金累计值。

## 4. 功能需求

### FR-1 邀请信息追加激活人数与佣金

- 用户列表“邀请信息”列继续展示邀请人数、收益和邀请人 ID，并新增已激活邀请人数。
- 邀请信息顺序为 `邀请 <数量> 人 · 激活 <数量> 人 · 收益: <金额> · 佣金: <金额>`。
- 激活人数数据来源为现有用户字段 `aff_valid_count`。
- 佣金数据来源为现有用户字段 `aff_commission_quota`，展示格式复用现有额度格式化逻辑和货币单位。
- 当用户没有邀请相关信息时，继续显示现有空状态 `—`。
- 当用户存在佣金累计值但没有邀请人数、邀请收益或邀请人 ID 时，也应显示邀请信息内容，不能因佣金为零而遗漏非零佣金。

### FR-2 全站额度统计接口

- 新增一个 `GET` 接口，统计所有用户的总额度和剩余额度。
- 接口必须挂载管理员鉴权；未登录用户、普通用户和权限不足用户不得获得统计数据。
- 成功响应至少包含：
  - `total_quota`：全站总额度；
  - `remaining_quota`：全站剩余额度。
- `total_quota` 的计算口径为所有用户 `quota + used_quota` 的总和。
- `remaining_quota` 的计算口径为所有用户 `quota` 的总和。
- 无用户数据时返回成功响应，两个值均为 `0`。
- 查询失败时沿用项目统一错误响应，不泄露 SQL、连接串或数据库内部错误细节。

### FR-3 用户页面统计展示

- `/users` 页面加载时请求统计接口。
- 统计盒子放置在条件选择栏中“角色”筛选项右侧，视觉高度与角色筛选项一致。
- 统计盒子显示顺序为：`全站总额度 <金额> | 全站剩余额度 <金额>`，中间使用竖分割线。
- 金额展示复用页面现有货币/额度格式化能力，保持当前系统货币设置和 tokens 模式兼容。
- 统计请求加载中、失败或无数据时不得阻塞用户列表；页面需要保留可用的筛选和列表能力。加载中或失败时统计盒子保留布局并显示 `—`。

## 5. 数据与外部约束

- 用户列表已经从后端返回 `aff_valid_count`、`aff_history_quota` 等邀请字段；后端模型已有 `AffCommissionQuota` / `aff_commission_quota` 字段，前端用户类型目前需要补充这些字段。
- 额度统计应直接聚合用户表现有的 `quota` 和 `used_quota` 字段，不读取消费日志、不修改余额数据。
- 聚合查询必须兼容 SQLite、MySQL 和 PostgreSQL，优先使用 GORM 聚合能力或数据库无关的查询表达式。
- 金额/额度结果需要使用能够承载全站累计值的整数类型，避免在数据库扫描、Go 响应结构或前端解析阶段发生 32 位截断。
- 路由复用现有 `/api/user` 管理员路由组和 `AdminAuth` 鉴权能力，路径为 `/api/user/stats/quota`。

## 6. 交互与状态

### 6.1 用户列表

- 现有列表、分页、筛选和排序行为保持不变。
- 邀请信息列新增激活人数和佣金文本，不新增独立列。
- 统计盒子与角色筛选并排展示；小屏幕下是否换行或隐藏，需结合现有工具栏响应式行为设计并在开发计划中明确。

### 6.2 异常和降级

- 统计接口失败时不影响用户列表查询和操作；统计盒子保留布局并显示 `—`。
- 管理员权限失效时按现有 API 鉴权和前端错误处理机制处理，不在前端绕过权限。

## 7. 验收标准

1. 用户列表邀请信息按“邀请人数、激活人数、收益、佣金”的顺序展示，激活人数使用 `aff_valid_count`，佣金使用 `aff_commission_quota`，并保持邀请人 ID 展示。
2. 佣金字段为零或缺失时，展示结果符合既有邀请信息空状态和金额显示规则，不出现 `NaN`、`undefined` 或错误货币格式。
3. 统计接口为 `GET`，未登录、普通用户和权限不足请求不能读取统计数据；管理员请求可成功读取。
4. 统计接口返回的 `total_quota` 等于所有用户 `quota + used_quota` 的和，`remaining_quota` 等于所有用户 `quota` 的和；无用户时均为 `0`。
5. 统计接口错误响应遵循项目统一响应约定，不暴露数据库内部细节。
6. `/users` 页面在角色筛选项右侧展示两个统计值，使用竖分割线分隔，并沿用现有货币/额度格式。
7. 统计接口失败或加载期间，用户列表仍可正常查询、筛选、分页和操作。
8. 新增前端文案完成 en、zh、zh-TW、fr、ja、ru、vi 七种 locale 的同步翻译。
9. 相关 Go 代码、前端类型和查询逻辑应覆盖本次新增的接口权限、聚合口径、佣金展示和统计区域状态；所有测试脚本编写与测试验证由开发者本人手动完成，AI 不编写测试脚本、不执行测试验证。
