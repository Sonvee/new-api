# 新旧版本数据可重复迁移开发计划

## 文档元信息

- **状态**：已实现，待开发者手动验证
- **创建日期**：2026-09-18
- **关联 PRD**：[新旧版本数据可重复迁移 PRD](../prd/06-repeatable-legacy-data-migration.md)
- **旧项目源码**：`E:\DockerApp\new-api`
- **新项目源码**：`E:\AIProject\new-api`
- **目标数据库**：PostgreSQL 15

## 1. 实施边界

### 1.1 要实现的内容

在仓库内新增独立的 `cmd/data-migrate/` 工具，用于把恢复到新 PostgreSQL 实例中的旧版本数据转换为当前新版本可正确使用的数据。

工具必须支持以下阶段：

1. 迁移前 schema 和数据状态检查；
2. dry-run，只分析并输出计划，不写入业务数据；
3. 正式迁移；
4. 迁移后校验；
5. 输出可保存的迁移报告。

### 1.2 明确不做的内容

- 不制作前端迁移页面；
- 不接入应用启动自动执行；
- 不自动停止或启动 Docker 容器；
- 不重复实现新项目已有的 GORM schema migration；
- 不支持 SQLite、MySQL；
- 不处理目标库已有新版本业务数据与旧数据的合并；
- 不修改旧项目源码；
- 不自动删除无法确认语义的旧字段或旧数据。

正式迁移前由开发者手动停止 `new-api` 容器，并确保目标库是由旧库恢复而来的全新迁移目标库。

## 2. 工具结构

新增目录及职责：

```text
cmd/data-migrate/
├── main.go       # CLI 入口、模式分发和退出码
├── config.go     # 参数解析、固定版本和文本报告
├── database.go   # PostgreSQL 连接
├── preflight.go  # schema、数据状态和全新目标库检查
├── migration.go  # dry-run、事务迁移、幂等标记和校验
└── README.md     # 使用前提和手动执行步骤
```

复用新项目已有的 PostgreSQL 驱动、GORM 和额度边界常量；迁移命令自行建立独立数据库连接，不调用应用启动初始化，也不依赖应用全局数据库状态。迁移专用逻辑只放在 `cmd/data-migrate/`，不得把迁移分支塞入应用启动、控制器或常规业务服务。

## 3. CLI 设计

建议命令形式：

```text
go run ./cmd/data-migrate --mode=check --dsn "$DATABASE_URL"
go run ./cmd/data-migrate --mode=dry-run --dsn "$DATABASE_URL"
go run ./cmd/data-migrate --mode=apply --dsn "$DATABASE_URL"
go run ./cmd/data-migrate --mode=verify --dsn "$DATABASE_URL"
```

要求：

- `check` 只检查，不写业务数据；
- `dry-run` 只读取并生成迁移计划、行数和异常项；
- `apply` 在单个 PostgreSQL 事务中执行所有数据变更；
- `verify` 只读取并检查迁移结果；
- 缺少 DSN、模式错误、schema 不符合要求时使用非零退出码；
- `apply` 必须显示迁移版本、源/目标版本、影响行数和报告摘要；
- 对固定版本之外的数据库拒绝执行，而不是静默猜测映射。

迁移记录使用工具自己的版本标识和执行记录，保证成功重复执行时不会重复发放奖励、重复记账或重复插入数据。失败事务回滚后允许重新执行。

## 4. 迁移前检查

### 4.1 数据库和运行状态

- 检查 PostgreSQL 版本和当前数据库连接；
- 检查目标 schema 已由新项目既有 migration 准备完成；
- 检查应用未在迁移期间写入数据库；
- 检查目标库符合“由旧库恢复、尚未产生新版本业务数据”的前置条件；
- 检查工具版本与固定的旧源码/新源码版本匹配。

### 4.2 Schema 检查

检查新版本必须存在的表、列、索引、唯一约束和必要默认值，至少覆盖：

- `users` 及其新增字段；
- 邀请关系、邀请奖励、充值佣金相关表；
- 认证、会话、审计、会计、钱包、任务和日志相关表；
- 新版本业务代码读取的关键列。

schema 检查只负责阻止不兼容执行，不负责创建或修改表结构。

### 4.3 数据检查

报告以下异常并默认阻止正式迁移：

- 重复主键或违反唯一约束的候选数据；
- 找不到关联用户的邀请、奖励、佣金和流水明细；
- 金额/额度为负数或超出目标类型范围；
- 关键认证数据格式不符合目标模型；
- 目标库已存在工具成功迁移记录但请求的版本不匹配；
- 目标库出现无法判定来源的新版本业务数据。

## 5. 数据迁移规则

### 5.1 通用规则

- 同名字段只有在源码语义和类型一致时才直接保留；
- 字段改名必须在映射表中显式记录；
- 旧版本计算字段不得直接当作目标持久化字段复制；
- 能从关系、明细或流水重建的值，以明细为权威来源；
- 无法确认语义的字段进入报告，保持目标默认值或原值，不自动猜测；
- 长期凭证保留；临时认证状态和登录会话失效；
- 所有写入使用参数化查询/GORM 操作，并在事务中执行。

### 5.2 用户和认证

- 保留用户主键、用户名、密码、显示名、角色、状态、邮箱、第三方身份标识、额度、用量、分组、邀请码、邀请人、备注和时间字段；
- 保留 API Token、Passkey 等长期凭证及其必要元数据；
- 新增字段使用源码定义的安全默认值或根据旧数据推导；
- 使 `user_sessions`、`auth_flows` 等登录会话和临时认证状态失效，不迁移可复用的临时认证状态；
- 为认证状态变更保留迁移报告，但不得输出密码、Token、Passkey 私密材料或可复用会话数据。

### 5.3 邀请和佣金

以旧源码的业务明细表和新源码的字段语义为准：

- `aff_count`：从邀请关系/用户邀请关系明细重建，不直接复制旧接口的 `invite_count`；
- `aff_valid_count`：根据有效邀请关系状态重建；
- `aff_reward_quota`：根据成功的邀请奖励明细汇总；
- `aff_commission_quota`：根据成功的充值佣金明细汇总；
- `affiliate_activated`：按照新源码定义的激活条件从关系和奖励状态推导；
- 保留无法转换但仍属于历史记录的原始明细，禁止重复生成奖励记录或佣金记录；
- 迁移后再次执行时，结果必须与第一次成功执行一致。

### 5.4 其他业务、日志和新增表

逐表建立迁移矩阵，至少标注：旧表/新表、主键、同名字段、改名字段、计算字段、新增字段、来源明细、冲突策略和校验 SQL。

范围包含：

- 渠道、模型、令牌、充值、兑换、订阅、任务等业务表；
- 请求/消费日志、审计日志和任务记录；
- 新版本新增但旧版本不存在的表：按业务语义决定初始化为空、从旧明细回填，或记录为不适用；
- 临时任务和认证状态：按安全规则失效，不保留可复用状态。

## 6. 事务、幂等和回滚

- `apply` 在一个 PostgreSQL 事务中执行所有数据变更；
- 迁移前由开发者执行数据库备份，工具不覆盖备份；
- 任一步骤失败时整体回滚；
- 迁移记录在同一事务中写入，避免出现“记录成功但数据未完成”；
- 使用稳定的业务主键、唯一键或迁移标记避免重复插入和重复汇总；
- 不允许通过删除业务数据来解决冲突；
- 对无法安全幂等的步骤先在 `dry-run` 阶段拒绝执行，并报告人工处理项。

## 7. 校验和报告

迁移报告至少包括：

- schema 检查结果；
- 每个步骤的读取行数、写入/更新行数、跳过行数和异常行数；
- 用户额度、邀请统计、奖励、佣金和流水的迁移前后汇总；
- 外键/关联完整性检查；
- 唯一约束和关键索引检查；
- 会话和临时认证状态失效结果；
- 可重复执行检查结果；
- 需要人工确认的字段和记录清单。

敏感字段只输出数量、哈希或脱敏标识，不输出密码、Token、Passkey 私密内容或可复用认证信息。

## 8. 实施顺序

1. 再次核对 PRD、旧/新源码和 schema，冻结迁移矩阵；
2. 创建 `cmd/data-migrate/` CLI 骨架和 PostgreSQL 配置；
3. 实现 schema 检查和 dry-run 报告；
4. 实现用户、认证和邀请财务迁移；
5. 实现其他业务表、日志表和新增表规则；
6. 加入事务、幂等标记、错误分类和报告持久化；
7. 实现迁移后校验；
8. 由开发者按手册在备份数据库上手动验证；
9. 根据手动验证结果修订映射矩阵和迁移规则。

每一步完成后都必须能明确说明：修改了哪些文件、处理了哪些表、如何回滚、由开发者执行什么手动检查。

## 9. 手动验证制度

根据用户确认：禁止 AI 编写测试脚本或执行测试验证。实现完成后，AI 只提供命令和检查清单，由开发者本人在自己的 PostgreSQL 环境中执行并记录：

- `check`、`dry-run`、`apply`、`verify` 四种模式；
- 迁移失败后的回滚；
- 成功后的重复执行；
- 用户邀请、奖励、佣金和额度汇总；
- 关键业务页面和登录流程；
- 备份恢复和回滚流程。

本计划不把未执行的验证标记为通过。

## 10. 风险与后续确认

- 旧项目和新项目继续变化时，当前工具不自动兼容新旧历史版本；需要更新固定版本标识、迁移矩阵和 PRD；
- 某些旧字段可能只有页面语义而没有可靠明细来源，必须在报告中列为人工确认；
- 日志、审计和任务数据量可能较大，正式实施前需由开发者根据实际数据量安排停机窗口和备份；
- 如果实际目标库已存在新版本产生的数据，本计划不允许直接执行合并迁移，必须重新确认需求。
